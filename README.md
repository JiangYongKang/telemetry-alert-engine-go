# telemetry-alert-engine-go

一套可在本地运行的**指标采集与告警判定引擎**。核心目标是让三件事——
并发写入、采样期间的规则调整、结果写出——在任意交织（包括下游持续失败）
下始终保持**一致且可解释**：

- 不静默丢数据：拒绝、背压、放弃全部有明确类型化信号与计数；
- 不重复计入：并发累加与串行等价；告警结论与写出都“恰好一次”推进；
- 可解释：每条告警结论携带产生它时的规则版本与阈值，判定依据可追溯。

## 目录结构

```
pkg/metrics/  指标模型与并发存储（基数上限、并发一致性）
pkg/alert/    告警规则状态机（阈值判定、For 持续时长、运行中规则变更）
pkg/sink/     有界写出器（Accepted / Busy / Abandoned 三态、重试、关闭交还）
pkg/engine/   编排层（周期采样判定、结论有序投递、背压传导）
cmd/demo/     本地演示：并发写入 + 规则变更 + 下游故障交织
```

## 1. 指标与标签模型

- 一条**时间序列**由 `Labels`（键值对集合）唯一标识。标签按 key 排序后
  规范化为字符串，例如 `{job="api",region="cn"}`。map 构造顺序不影响
  身份：相同逻辑标签集合在任何时刻产生相同的序列键（可复现）。
- 一次写入 `Sample{Labels, Value, Add}`：
  - `Add=true`：计数器语义，在当前值上累加；
  - `Add=false`（默认）：最新值语义，覆盖当前值。
- 并发一致性：存储用互斥锁把每条序列的“读—改—写”线性化。同一时间序列
  上任意并发 `Add` 的累积结果与按某个顺序串行执行**完全一致**
  （`go test -race` 下有对拍验证）。不同序列互相独立。
- **基数上限（取舍规则确定且可复现）**：存储在构造时设定活动时间序列
  上限 `maxCard`。
  - 已存在序列的写入**永远接受**（更新不受限）；
  - 新序列在活动数已达上限时**一律拒绝**，返回可类型断言的
    `*metrics.CardinalityLimitError`，并累计 `RejectedCount()`；
  - 不做随机淘汰、不按到达时间“挤掉”旧序列，因此相同输入集合下被拒
    结果是确定的。调用方（或 `Engine.Ingest`）据此得到
    `IngestResult{Accepted:false, Reason:"cardinality_limit"}`，
    数据不会悄悄消失。

## 2. 告警判定与规则变更语义

规则定义 `alert.Rule{ID, SeriesKey, Op, Threshold, ForDuration}`：
对指定序列按算子（`> >= < <= ==`）比较阈值；`ForDuration>0` 时要求
**连续**满足达到该时长才触发，`0` 表示立即触发。

每条规则维护独立状态机：

```
            满足(未满 For)                满足满 For
 inactive ───────────────► pending ───────────────────► firing
    ▲                         │                            │
    └──────── 不满足（清零）───┘                            │
    │                                                       │
    └──────────────────── 不满足（恰好一个 resolved）◄──────┘
```

- fired 之后持续满足**不会重复触发**；从 firing 退出时**恰好**产生一个
  `resolved`。`pending` 期间不满足则清零进度（pending→inactive 不发
  事件）。删除 firing 规则会补发 resolved，不留悬挂告警。
- **同一时刻对同一规则至多一个结论**；一个 tick 中多条规则分别独立。
- 规则定义是**版本化**的：`Upsert` 原子整体替换 spec（算子/阈值/
  ForDuration/序列键），版本号单调递增。语义保证：
  1. **新阈值立即生效**：自替换之后的每一次判定都引用新版本，事件中
     的 `Rule`/`Version` 即产生该结论时实际依据的阈值——旧阈值不可能
     影响任何结论；
  2. **不重复触发**：替换动作本身不产生事件，已 firing 的规则不会因换
     阈值而再次 fired；
  3. **不丢进度**：阶段与“连续满足起始时间”在变更中保留。若当前值对
     新阈值仍满足，跨版本的连续时间继续累计；若不再满足，则按新阈值
     正常给出 resolved。
- 所有事件含 `RuleID / Value / Rule(含阈值) / Version / At`，判定依据
  完整可解释（单测与 demo 日志均逐条打印）。

## 3. 背压与放弃规则（结果写出）

`sink.Writer` 是有界异步写出器，`Submit` **永不阻塞**，结果三态可区分：

| 结果 | 含义 | 调用方应做什么 |
|---|---|---|
| `Accepted` | 已进入队列，受“不丢”保证 | 无需处理 |
| `Busy` | 缓冲耗尽（下游持续失败占满队列同此表现），是**暂时**信号 | 稍后用**同一份**数据重试 |
| `Abandoned` | **确定性、终结性**放弃，`Reason` 区分原因：`payload_too_large`（超单条大小上限，重试无意义）、`sink_closed`（已关闭） | 记录/告警；不会、也不应再回写 |

投递与重试：

- 后台协程整批投递，下游接口要求**原子确认**（整批成功或整批失败）。
  只有下游返回成功后事件才从队列弹出，因此失败时整批原样重试，
  **既不会漏送已接受事件，也不会重复写出**。
- 失败按指数退避重试；重试期间队列无法腾出空位，`Submit` 持续得到
  `Busy`，从而把下游故障**转化为对上游的背压**。
- `Close(ctx)`：停止接收（新提交→`Abandoned/sink_closed`），在 `ctx`
  截止前尽力排空；仍未送达的事件**按入队顺序作为返回值交还调用方**
  （`ErrUndelivered` 标记，计数 `Undelivered`）。此后队列所有权转移，
  worker 不会再把这些事件写向任何下游——**恢复后不回写已放弃/已交还
  的数据**。

`engine.Engine` 在其上保证结论有序与不丢：

- 每个 tick：快照存储 → 序列键排序后逐规则判定（顺序可复现）→ 结论按
  产生顺序投递；
- sink 返回 `Busy` 时结论进入引擎 FIFO `pending`，之后**每个 tick 优先
  重试**（不依赖新事件到来），恢复后按序补投；
- `Abandoned` 的结论显式记入 `Dropped()`（含原因），绝不静默；
- `Shutdown` 在截止时间内反复喂入 pending，再关闭 sink，最终仍无法
  送达的事件（引擎滞留 + sink 交还）统一向上交还。

## 4. 本地验证

要求 Go 1.25+（开发环境验证于 Go 1.26）。

```bash
# 编译
go build ./...

# 全量单元/集成测试，开启竞态检测（测试日志含输入、状态变化与判定依据）
go test ./... -race -count=1 -v

# 只跑核心交织场景
go test ./pkg/engine -race -v -run TestConcurrentIngest

# 本地演示：并发累加 + 基数拒绝 + 阈值变更 + 下游故障/恢复
go run ./cmd/demo
```

测试覆盖要点：

- `pkg/metrics`：同一序列高并发累加对拍串行基准；多序列独立；基数
  上限拒绝的类型化原因、计数与可复现性；高并发混合“已存在/新”序列。
- `pkg/alert`：立即/For 持续触发不重复；pending 进度中断与保留；
  阈值/算子在采样中途变更后立即按新版本判定、进度不丢、结论不重复；
  删规则补发 resolved；固定脚本对拍手工串行基准（类型/版本/阈值逐条
  核对）。
- `pkg/sink`：三态结果与原因；故障期重试、恢复后恰好送达一次且有序；
  Busy 在排空后可重新接受；`Close` 交还顺序且不回写；调用方缓冲区
  复用不污染已入队数据。
- `pkg/engine`：并发写入 + 规则变更 + 下游故障在固定 tick 脚本下交织，
  送达事件序列与串行基准逐条一致，计数器并发结果等于串行累加，
  拒绝/背压/送达计数全部可对账；下游持续失败时 `Shutdown` 显式交还
  未送达事件。

## 设计取舍与已知边界

- 指标存储采用单把互斥锁换取简单可证的线性一致性；序列规模超大时可
  再做分片，当前基数上限本身就是为控制扇出而设。
- sink 的“不丢”止于进程生命周期：`Close` 交还的未送达事件需要调用方
  自行持久化或降级处理，引擎不内置落盘。
- 下游 `Write` 应尊重传入 `ctx` 的取消信号，使 `Close(ctx)` 能及时
  中断在途写入；极端竞态下“写入在途成功”与“关闭超时交还”可能同时
  发生，交还的事件可能恰好已到达下游，调用方重放时需具备幂等键。
